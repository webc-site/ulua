# 性能优化

本 skill 定义本仓库做性能优化的统一纪律。核心一句话：任何优化都必须由 profile 提出、由汇编证实、由配对评测定夺，且只有在被测用例上真的变快之后才允许合并。

## 1. 优化的优先级次序

1. 架构级、能提升整体性能的大优化优先：派发结构、内存布局、数据通路、状态机分层这类改动，收益是全局的。
2. 其次是指令级的中观改动：热/冷路径分离、超级指令（把常相邻的几条字节码融合成一条 handler）、分支形状、循环展开。
3. 最后才是局部微调。不要在没弄清结构问题之前陷入逐指令抠算。
4. 手写汇编（dynasm-rs）、SIMD（fearless_simd）属于允许的手段，但它们是达成架构目标的手段，不是目标本身；任何一条走不通就立刻回退，不留半截实现。

## 2. 开工前的准备

1. 开分支与隔离工作区，主工作区保持干净：
   `./fork.sh opt-<topic>`，后续所有编辑、构建、profile、bench 都在 worktree 内做。
2. 立基线，作为一切比值的分母，并把它留存到会话结束：
   `benchmarks/runner` 产出的 JSON 就是基线（例如 `/tmp/bench-base.json`）。
3. 先测噪音地板：同一份二进制重复测 3 次。若某用例的重复间波动本身就有 5%，那"5% 收益"的判据对它无效，必须换更长窗口的用例或提高 runs。
4. 明确对照组：不仅要盯住要改进的用例，还要钉住现有优势用例，它们只允许持平（回退阈值 2%）。

## 3. 定位瓶颈：必须基于证据

1. 先排除伪因。同一份字节码用 `--text` 逐字节对比 cpp 与 ulua 的输出，确认差异不在编译器；再确认问题不在分配器、GC、缓存策略等实现细节上。
2. profile 要落到具体地址：采样 profiler 得到的 self-time 必须用反编译对齐到指令。
   `samply record` / `samply collect` 取热点，`llvm-objdump -d` 或 `cargo rustc --release -- --emit=asm` 看形状。
   关注这几类信号：依赖串是否过长（取指→查表→间接跳转是天然串行链）、间接跳转是否全 VM共享一条 `br`（BTB 只有一个 site）、是否有 `csel`/`b.hi`/多余的 `mov`/被 spill 的常驻变量、热快路径在 I-cache 上彼此相距多远。
3. 做 A/B 反证，而不是只靠读数推测。把 cpp oracle 里的某个特性关掉（例如 `VM_USE_CGOTO`）重编一份，看退化幅度能不能覆盖我们的差距。能覆盖，才说明机制判断成立。
4. 热点集合不靠猜。用动态统计（本仓库有 `vm-opcount` feature，产出 opcode 直方图与 opcode 转移计数）来选热臂子集与可融合的相邻指令对；转移计数直接给出相邻性证据。
5. 借用外部实现的经验时，先 clone 到 /tmp 再读，不要凭印象：
   LuaJIT 的 `vm_arm64.dasc`、`lj_asm_arm64.h`、`lj_dispatch.c`、`lj_opt_fold.c` 是手写派发与 trace 优化的范本。吸收之前先检查不变式是否兼容：例如 LuaJIT 的 TValue 是 8 字节 NaN-boxing 联合，而 Luau 是 16 字节 TValue，照搬会破坏与 cpp 的等价性，这类"技巧"只能学思路不能改数据布局。

## 4. 每一步都要过的门禁

1. 静态检查（用不带 --fix 的版本，避免格式化噪音混进 diff）：
   `cargo +nightly clippy -q --tests --all-targets --all-features -- -D warnings -W clippy::absolute_paths`
   要求零警告、零 `#[allow`。若某条优化确实需要豁免（例如 nightly 特性带来的 `incomplete_features`），必须先取得用户同意，把它做成仓库内唯一、有记录、有范围的例外，并在 `review.md` 写明理由，同时收紧门禁正则以免漏检。
2. 正确性：`./test.sh` 全绿，语义以 `./cpp` 为 oracle。子代理不跑这条，由主流程跑。
3. 汇编门：改完必须上机核对代码形状是否真按预期落地（例如每个热 opcode 尾部是否各自一条 `b`、条件跳转是否不再折成 `csel`、handler 是否没有 prologue/epilogue）。编译器没照计划做，就等于这一步没做。
4. 针对性正确性用例：新的派发/展开路径不能只靠既有测试兜底。要写定向用例钉住：热循环内抛错的展开、`pcall` 捕获、协程跨热臂 yield/resume、中断钩子在热臂上的命中与续跑、以及钩子观察到的行号区间（把"pc 有没有走错"钉死在源码行范围内）。
5. 交叉编译门：非热点架构（wasm32-unknown-unknown、wasm32-wasip1）至少要 `cargo check` 通过、测试通过，回退路径完好。
6. Rust 化与性能并行推进：允许在热路径保留必要的原始指针与 unsafe（C-ABI 兼容与性能所必需，须写清安全不变式），但非热模块要持续按 Rust 惯用法改造，减少 C 风格指针算术、减少 unsafe 面。安全改造本身也要过性能门，不能拿性能换可读性。

## 5. 评测与合并纪律

1. 小步迭代，一个想法一个提交，每一步都独立可回滚。禁止把多个未验证的改动攒成一个大提交。
2. 评测用配对 A/B：同一时刻、同一机器、同一 feature，用两个二进制（改动前/改动后）交替各跑 3 次，取最好值比。不要用不同时间点产出的 JSON 直接相除，那会把依赖升级、后台负载、系统热状态混进结论。
3. 判据：在改动目标用例上要有超过噪音地板的实收益（默认门槛 5%）。达标才保留；不达标就丢掉这一步，不要攒着"以后可能有用"。
4. 收益之外的回退同样要审：优势用例、JIT 模式、compile/analysis 组都要复测，确认没有跨组回退，`benchmarks/results*.json` 的指纹一致性告警不出现。
5. 区分真回退与二进制布局彩票：一个只有几毫秒的短窗口用例涨 8%，而同形状的长窗口用例持平，且被改动的源码路径逐字未变，这通常是代码地址/对齐变化带来的抖动，不是语义回退。要复测、拉长窗口、找同形对照，再下结论。
6. 提交纪律：`git add` 只写精确路径（禁 `-A`、禁 `.`），提交信息一行英文加一行中文，形如
   `perf(vm): split conditional-jump tails so pc stops folding into csel 条件跳转拆双尾，pc 推进不再折成 csel`。
   不 push、不开 PR，除非用户明确要求。
7. 合并前先把目标分支拉进来对齐，冲突解完重跑全套门禁（静态检查、测试、交叉编译、评测），在合并提交信息里写清带进了什么、保留了什么。
8. 每一步的结论要落进可复查的地方：目标用例的前后数值、汇编形状的核对结果、被丢掉的想法与丢掉的原因。被丢掉的想法在文档/提交信息里留一句"实测无收益，故未采纳"，避免下轮重复踩。

## 6. 收尾

1. 跑一轮完整 `./bench.sh`（全部后端与所有分组），确认全局无回退。
2. 更新文档：把本轮实测数据与机制解释写进对应的性能文档，说明哪些优化被采纳、哪些被测量否决。
3. 清理探针残料：/tmp 下的实验二进制、备份文件、临时 JSON 都可以删，但基线 JSON 留到本轮结论确定之后再删。仓库内若留下 A/B 用的备份文件（例如改过的 `cpp/` 下源码），必须还原到原始状态再收尾。
4. 最后确认工作区干净：`git status --porcelain` 为空，除本次要交付的改动之外没有夹带格式化噪音。

## 7. 常见坑

1. 用 `cmd | tail; echo $?` 取状态，量到的是 `tail` 的退出码，会得到假绿。要么重定向到日志后再取 `$?`，要么用 `pipestatus`。
2. `./sh/clippy.sh` 与 `./clippy_extra.sh` 会全仓重写格式，可能与门禁无关地把上百行别人的代码拖进 diff。验收改动本身用不带 `--fix` 的 clippy 与 `cargo +nightly fmt --check`；跑完自动修复脚本后要审 `git status`，把无关文件 `git checkout --` 回去。
3. 游离的 workspace（`fuzz/`、`benchmarks/runner`）不在根 workspace 的 members 里，`--all-targets` 覆盖不到，需要各自单独跑门禁用脚本。
4. 共享的 target 目录被多个 worktree 复用时可能产生陈腐的构建产物，表现为莫名其妙的编译错误。测试门禁固定用独立的 `ULUA_TARGET_BASE`。
5. 空栈上读返回值：断言状态之前先取结果，出错/让出时会踩到越界哨兵，报错信息就不是本用例真正要说的话。先断言 resume 状态，再读返回栈。
6. 需要固定编译选项才能钉住指令序列的用例（例如按 `currentline` 区间断言），必须显式写死 `optimization_level` 并按需 `skipCodegen`，否则测的不是你以为的那段代码。
